# planner-fixtures — Go-exported cache-planner parity fixtures

`planner.json` and `wire.json` are **generated by the Go cache engine**
(`public/cacheengine/export_fixtures_test.go`). Do not edit them by hand.

**The Go engine is the source of truth.** A TS/Go disagreement is either a TS
bug or a stale fixture needing regeneration — never a hand-edit of these files.

Regenerate:

```bash
cd public && CAVE_EXPORT_PLANNER_FIXTURES=1 go test ./cacheengine -run TestExportPlannerFixtures
```

Drift gate: `TestPlannerFixturesMatchCheckedIn` (always-on in
`go test ./cacheengine/...`) regenerates the fixtures in memory and fails on
any byte difference from these files, and fails if they are missing.

## Files

Both files share one shape: `{catalog_sha256, cases: [...]}`. The header's
`catalog_sha256` is the sha256 of the exact
`public/shared/provider-catalog/catalog/current.yaml` bytes the exporting
engine ran against (the same identity as the TS package's `CATALOG_SHA256`):
fixture cache economics come from that catalog, so a price/threshold edit
changes the hash and the drift gate fails with its cause named instead of the
economics recoupling silently.

- `planner.json` — planner cases: `{name, config, steps: [{request, plan}]}`.
  Steps within a case run in order against one engine instance, so stateful
  contracts (prefix drift) are representable; most cases have one step.
  `request` mirrors Go `PlanRequest` (profile inlined, `ttl_seconds` instead
  of a Go duration, segment `content` as a raw string); `plan` is the Go
  `Plan` struct's own JSON. `expected_net_input_rate_units` are input-rate
  units (one unit = one token at full input rate), never dollars.
- `wire.json` — provider-native wire cases (Anthropic `/v1/messages`, OpenAI
  chat + responses, Bedrock converse + invoke): `{name, request, result}`.
  `request.body` and `result.body` are raw strings and must match
  **byte-exactly** — they pin the splice-vs-reserialize behavior of each Go
  wire (Anthropic/OpenAI byte-splice; Bedrock reserializes sorted-key JSON).
  `result.plan` carries `profile_id`/`mode`/`attribution`; provider profile
  facts otherwise come from the catalog, not from these fixtures.

## Contract (unchanged from cacheengine)

Original bytes are preserved on every uncertain path (malformed, unsupported,
caller-managed, record mode, drift, volatile prefix); optimizers add
provider-native hints only; no verified-dollar minting — `claim_basis` is at
most `inferred` and `verified_savings_usd` never appears here as anything but
absent/zero.
